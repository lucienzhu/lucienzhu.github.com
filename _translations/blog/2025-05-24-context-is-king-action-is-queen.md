使用同一个模型的两个 Agent，可能交付完全不同的结果。一个反复询问用户已经提供的信息，另一个理解了任务，却无法采取完成任务所需的动作。

这些失败，都指向模型选择之外的产品工作：**Context 决定 Agent 理解什么，Action Space 决定它能交付什么。** 两者连接得怎样，影响它能否进入日常工作。

## 帮助人开始行动

空白页经常是阻力。Agent 可以先起草一个版本，汇集相关材料，或者把模糊请求变成可检查的计划。整项任务还没有自动化，这一步也已经可能产生价值。

环境同样重要。订旅行，需要浏览器和预订服务；做网站，需要文件、编辑器和预览。Agent 要从环境获得反馈，才能知道动作是否产生了预期效果。

一个有用的产品，会让这个循环可以理解：人的意图、准备采取的动作，以及观察到的结果。使用者需要足够的信息，判断应该继续还是纠正方向。

## Context is King

“准备一份发布公告”，留下了许多未说明的决定：受众是谁，哪些描述已经确认，组织适合什么语气，公告准备发在哪里？

相关上下文，可以减少新一轮解释。它可能来自当前对话、工作文档、过往决定或明确反馈。产品需要取出有用部分，还要避免旧假设覆盖后来的纠正。

重复使用真的改善了工作，优势才会积累。知识库堆满无关材料，帮助有限；记住的偏好用错任务，甚至会让结果更差。上下文的质量，取决于相关性、准确性，以及用户能否更新它。

产品的传播速度与持续用途，也需要分别评价。重复任务更适合检验上下文是否产生了价值：用户是否解释得更少，纠正得更少，结果是否更贴合需要？

连续性可以让产品值得留下来。这个价值建立在有效服务与信任之上，包括清楚的访问边界，以及对记忆内容的控制。

## Action is Queen

上下文需要通过合适的动作转成成果。营销助手可能需要起草内容、准备不同渠道的素材；编程助手可能需要修改文件、运行检查，再查看页面效果。

动作空间是产品设计的一部分。底层控制提供灵活性，也把更多执行步骤留给 Agent；设计合理的高层工具，可以封装领域知识，并返回有助于判断任务是否成功的反馈。

有用的工具，还需要保留后果不同的操作：存草稿与正式发布，修改文件与验证修改，都有各自的作用。Agent 需要识别失败，在可恢复的地方恢复，并在需要人作决定时引入人。

行业经验，帮助团队定义这些动作及其完成标准。工具数量增加，只有在 Agent 能有效选择和使用时，才会转成能力。

## 把完整循环放进评估

Context 与 Action 应该放在真实任务中共同检验：有没有使用已经确认的约束，修改有没有产生预期结果，人还需要多少检查和返工？

这些答案，也影响商业模式。按结果收费，需要定义清楚结果，并有办法判断交付。一次好看的演示，或者一长串工具调用，本身还不足以证明价值。

好的产品体验，减少了从人的意图到可接受结果之间的负担。理解使用者，以及提供可靠行动，是这项工作相连的两部分。
